# Smart Edu Center — Master Delivery Plan

هذه هي قائمة التنفيذ الوحيدة المعتمدة للمشروع الكامل. الغرض منها أن يستطيع أي مطور أو Agent معرفة **التاسك التي عليها الدور** دون تخمين أو فجوات.

التفصيل الهندسي لكل مرحلة موجود في [`TECHNICAL_EXECUTION_BACKLOG.md`](TECHNICAL_EXECUTION_BACKLOG.md). عند بدء تطوير تقني، يجب تنفيذ `CURRENT_TECHNICAL_TASK` المحددة هناك.

## بروتوكول اختيار التاسك التالية

1. اقرأ `AGENTS.md` ثم هذا الملف.
2. ابحث عن `CURRENT_TASK` أدناه؛ هذه هي المهمة الوحيدة التي يبدأ بها العمل.
3. لا تبدأ مهمة تعتمد على مهمة غير مكتملة.
4. عند الإكمال: نفّذ معايير القبول وبوابة الجودة، غيّر `[ ]` إلى `[x]`، وانقل `CURRENT_TASK` إلى أول مهمة تالية متاحة.
5. إذا توقفت المهمة بسبب قرار أو خدمة خارجية، غيّرها إلى `[!]`، سجل السبب، وانتقل فقط إلى مهمة لا تعتمد عليها.
6. الحالات: `[ ]` لم تبدأ، `[-]` قيد التنفيذ، `[x]` مكتملة، `[!]` متوقفة.

```text
CURRENT_PHASE: 1 — الأساس التقني
CURRENT_TASK: FND-008 — CI لفحص الجودة على كل Pull Request
LAST_COMPLETED: FND-008-03 — فحص migrations بلا بيانات اعتماد أو تطبيق DB
```

## مبادئ ثابتة

- المنتج منصة واحدة بنموذجين: **سنتر تعليمي** و**مدرس مستقل**.
- Web PWA أولًا؛ Flutter بعد إثبات حاجة تجارية واضحة.
- Arabic RTL وMobile-first، مع كفاءة تشغيل على الديسكتوب.
- عزل العملاء بـRLS إلزامي، ولا يُستخدم `service_role` في المتصفح.
- لا Marketplace ولا ERP كامل ولا بث فيديو مملوك في المراحل الأولى.
- لا تُبنى ميزة بلا مشكلة مثبتة ومعيار نجاح.

## بوابة الجودة لكل مهمة

- معيار القبول الوظيفي ناجح، بما فيه الحالات السلبية.
- `npm run lint` و`npm run typecheck` و`npm run build` ناجحة.
- اختبار RLS والصلاحيات عند لمس البيانات.
- مراجعة RTL والموبايل والديسكتوب عند لمس الواجهة.
- تحديث الوثائق والخطة، ثم Commit/PR واضح وPreview صالح.
