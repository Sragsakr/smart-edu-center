# ADR-0001 — البُعدان المستقلان ومستويات المنتج

- **Status:** Accepted
- **Date:** 2026-09-11
- **Supersedes:** النموذج الضمني السابق الذي كان يعامل `tenants.account_type` كنوع تجاري وحيد
- **Related:** [ADR-0002](0002-entitlements-over-rbac.md) · [`PRODUCT_VISION.md`](../PRODUCT_VISION.md)

## Context

الـcanonical baseline كان يعرّف `tenants.account_type ∈ ('center','independent_teacher')` فقط، ويستخدمه في الواجهة والإدارة كتصنيف وحيد للمساحة. هذا يجعل «نوع العميل» و«ما اشتراه العميل» مفهومًا واحدًا، وهو ما يمنع:

- بيع مستويات منتج مختلفة لنفس نوع العميل.
- ترقية العميل دون إعادة إنشاء Tenant أو نقل بيانات.
- بناء الكتالوج بشكل مختلف لنموذج المدرس مقابل السنتر دون تكرار المنطق.

## Decision

نفصل بعدين مستقلين تمامًا:

1. **Customer Type** — `tenants.tenant_type ∈ ('teacher','center')`
   - يحدد **شكل الكتالوج والتنقل والتنظيم**.
   - **لا** يحدد أي ميزة أو اشتراك.
2. **Product Level** — `tenants.product_level ∈ ('operations','management_platform','learning_platform')`
   - يحدد **ما هو مشتراة**.
   - **لا** يحدد شكل الكتالوج.

القيم التجارية المعتمدة: `teacher` / `center` (بدل `independent_teacher`، مطابقة للمصطلح التجاري).

يُمنع في الكود أي قرار تجاري مبني على `tenant_type`. يُستبدل بـ`hasEntitlement()`. يبقى `tenant_type` مشروعًا فقط لتشكيل التنقل والافتراضات والواجهة.

## Consequences

**إيجابيات:**
- نفس الـTenant والبيانات تستمر عند الترقية: تعديل صف + تفعيل entitlements + Audit.
- مدرس مستقل يمكنه شراء `learning_platform` كاملًا، وسنتر يمكنه البقاء على `operations`.
- لا تكرار منطق الكتالوج بين النموذجين.

**سلبيات/تكاليف:**
- `account_type` يجب إعادة تسميته في الجداول والكود والاختبارات.
- يلزم انضباط مراجعة لمنع تسرّب مقارنات `tenant_type` التجارية إلى الكود.
- الترقية/التخفيض تحتاج مسار عمل إداري مع Audit.

## Alternatives considered

| البديل | سبب الرفض |
|---|---|
| إبقاء `account_type` واستخدام `plan` فقط | يدمج نوع العميل بالمستوى ويمنع مستويين مختلفين لنفس النوع بمرونة |
| Enum واحد مثل `center_ops` / `teacher_lms` | انفجار قيمي، ويعيد الخلط الذي نمنعه، ويفسد الترقية |
| جداول منفصلة لكل نموذج | تكرار كامل للكتالوج والمجموعات والحضور والتحصيل بلا قيمة |
| تطبيقات منفصلة | مرفوض صراحة في قرار المالك وفي حدود المنتج |

## Compliance

- يُنفَّذ في المخطط عبر `P01-06` (Commercial Foundation).
- يُختبر باختبارات تفيد أن نفس الكتالوج يعمل للنموذجين، وأن الترقية لا تفقد بيانات.
